# MK1 Stream Roster — описание проекта

## 1. Идея

Одностраничное веб-приложение для стрима с ростером персонажей Mortal Kombat 1.
Стример нажимает на портрет персонажа, после чего поверх карточки появляется
анимированная отметка, показывающая, что персонаж «погиб» или выбыл. Повторное
нажатие отменяет отметку.

Страница должна одинаково хорошо работать:

- как обычная страница в браузере;
- как Browser Source в OBS;
- после публикации на GitHub Pages.

## 2. Основной пользовательский сценарий

1. Стример открывает ростер.
2. Нажимает на портрет выбывшего персонажа.
3. Поверх портрета проигрывается короткая анимация зачёркивания.
4. Карточка остаётся визуально помеченной до повторного нажатия или сброса.
5. Повторное нажатие возвращает персонажа в активное состояние.
6. Кнопка «Сбросить всё» возвращает весь ростер в исходное состояние.

## 3. MVP

- Полный актуальный ростер в виде адаптивной сетки: основные бойцы, Kameo и DLC.
- Имя персонажа и его портрет на каждой карточке.
- Два состояния карточки: `active` и `eliminated`.
- Включение и выключение состояния по клику.
- Составной эффект выбытия: обесцвечивание портрета, затемнение, кровь и две
  анимированные красные линии.
- Обратная анимация или плавное исчезновение отметки при отмене.
- Кнопка общего сброса с защитой от случайного нажатия.
- Сохранение состояния в `localStorage` после перезагрузки страницы или OBS.
- Адаптация под разрешение стрима, в первую очередь 1920×1080.
- Управление непосредственно через окно `Interact` у Browser Source в OBS.
- Публикация на GitHub Pages.

## 4. Визуальное направление

Основной референс — официальный экран ростера MK1, но без буквального
копирования его интерфейса. Выбранное направление:

- тёмный фон;
- металлические, каменные или дымные фактуры;
- золотистые акценты для активных персонажей;
- две пересекающиеся кроваво-красные линии для выбывших персонажей;
- брызги или подтёки крови как короткий вторичный эффект;
- затемнение и полное либо почти полное обесцвечивание портрета;
- короткая резкая анимация смерти длительностью примерно 450–700 мс;
- спокойная зацикленная анимация огня и дыма в фоне или по краям ростера;
- минимум постоянного движения, чтобы интерфейс не отвлекал от стрима.

Зачёркивание и переход карточки в чёрно-белое состояние делаются через CSS и
SVG. SVG-линии анимируются через `stroke-dashoffset`, кровь — через маску или
короткую прозрачную текстуру. Для фонового огня допускается оптимизированный
зацикленный WebM или animated WebP. GIF не используется из-за большого размера,
ограниченной прозрачности и отсутствия удобного управления анимацией.

Three.js в первой версии не используется: для плоской сетки и двухмерных
эффектов он не даёт визуального преимущества, но увеличивает bundle и нагрузку
на GPU во время игры и стрима. Если позднее появится утверждённая 3D-сцена,
например камера, частицы и объёмный логотип, это будет отдельным этапом.

## 5. Режимы отображения

### Интерактивный источник OBS

Для MVP используется одна страница. Она добавляется в OBS как Browser Source и
открывается для управления через контекстное действие `Interact`. Стример
нажимает прямо на карточки; курсор и окно взаимодействия в эфир не попадают.
Сброс можно выполнить кнопкой в интерфейсе взаимодействия или горячей клавишей.

Фон страницы проектируется так, чтобы его можно было переключить между
полноценным оформлением и прозрачным overlay-режимом параметром URL, например
`?background=transparent`.

### Отдельная панель управления

Панель в обычном Chrome и Browser Source в OBS не синхронизируются через общий
`localStorage`, поскольку работают в разных браузерных профилях. Если заказчику
понадобится управление из отдельного браузера или с телефона, добавляется
realtime-синхронизация через небольшой backend. Это не входит в MVP.

## 6. Предлагаемый стек

- React;
- TypeScript;
- Vite;
- Tailwind CSS;
- SVG/CSS для эффекта зачёркивания;
- WebM или animated WebP для оптимизированных зацикленных декоративных эффектов;
- `localStorage` для сохранения состояния;
- GitHub Actions для публикации на GitHub Pages.

Отдельный сервер и база данных для MVP не нужны: всё работает непосредственно
в браузере стримера.

## 7. Инженерные требования

- Компоненты имеют одну ответственность и понятный публичный интерфейс.
- Данные ростера отделены от UI и проверяются TypeScript на этапе сборки.
- Состояние персонажей хранится централизованно, без дублирования.
- Производное состояние не записывается в state.
- Для простого состояния используются React API, без лишней state-библиотеки.
- Tailwind отвечает за layout, адаптивность и дизайн-токены; сложные keyframes и
  SVG-эффекты изолируются в минимальном слое CSS.
- Интерактивные элементы доступны с клавиатуры и имеют корректные состояния
  `focus-visible`.
- Поддерживается `prefers-reduced-motion`.
- Нет комментариев, мёртвого кода, неиспользуемых зависимостей и абстракций без
  реальной задачи.
- Изображения загружаются лениво, а критичные декоративные ресурсы — заранее.
- Сборка проверяется линтером, TypeScript и production build.

## 8. Модель данных

Для каждого персонажа достаточно хранить:

```ts
type Fighter = {
  id: string;
  name: string;
  image: string;
  group?: "main" | "kameo" | "dlc";
};
```

Состояние выбывших персонажей можно хранить как массив `id`:

```ts
type EliminatedFighters = string[];
```

## 9. Требования к изображениям

Портреты собираются с официальной страницы ростера автоматизированным скриптом,
а не скачиваются вручную. В проекте они хранятся локально, чтобы не зависеть от
доступности и структуры внешнего CDN. Требования к подготовленным файлам:

- в одном визуальном стиле и ракурсе;
- с одинаковым соотношением сторон;
- размером хотя бы 500×700 px;
- в WebP или PNG;
- с прозрачным фоном либо с одинаковым фоном у всех;
- с понятными латинскими именами файлов, например `scorpion.webp`.

- основные бойцы, Kameo и DLC лежат в отдельных каталогах или имеют явную группу
  в manifest-файле;
- для каждого ресурса сохраняется источник, чтобы ростер можно было обновить.

> Изображения и фирменные материалы Mortal Kombat принадлежат их
> правообладателям. Перед публичным размещением стоит согласовать с заказчиком,
> какие материалы можно использовать и для каких целей.

## 10. Принятые решения и открытые вопросы

Принято:

- размеры и прозрачность настраиваются в ходе реализации;
- в ростер входят все персонажи;
- эффект смерти сочетает кровь, красный крест и обесцвечивание;
- основное управление выполняется прямо в OBS;
- портреты берутся с официальной страницы ростера;
- используется Tailwind CSS;
- качество и чистота кода являются обязательной частью готовности.

Остаётся проверить на прототипе:

1. Точный порядок и группировку основных, Kameo и DLC-персонажей.
2. Должны ли имена быть видны постоянно.
3. Нужен ли звук при зачёркивании.
4. Нужна ли горячая клавиша общего сброса.
5. Как долго состояние должно храниться после завершения стрима.

Последний вопрос особенно важен: если управлять ростером нужно с телефона или
другого компьютера, одного GitHub Pages и `localStorage` уже недостаточно —
понадобится синхронизация через внешний сервис или небольшой сервер.

## 11. Возможные улучшения после MVP

- выбор одного из нескольких эффектов выбытия;
- настройка цвета, скорости и толщины зачёркивания;
- горячие клавиши и управление с Stream Deck;
- история действий и кнопка «Отменить»;
- счётчик оставшихся персонажей;
- фильтры по основным, Kameo и DLC-персонажам;
- импорт и экспорт текущего состояния;
- удалённое управление с телефона;
- звуковой эффект;
- режим «случайный следующий персонаж».

## 12. Предлагаемые этапы

1. Создать React/Vite/Tailwind-проект и инженерную конфигурацию.
2. Собрать manifest и скачать изображения с официальной страницы.
3. Создать адаптивную сетку на временно выбранном размере viewport.
4. Реализовать интерактивную карточку и составной эффект смерти.
5. Добавить огонь, сохранение состояния и прозрачный режим.
6. Проверить производительность и взаимодействие в OBS.
7. Подкорректировать размеры и визуальные параметры по результатам прогона.
8. Создать Git-репозиторий, загрузить его на GitHub и настроить GitHub Pages.

## 13. Критерии готовности MVP

- Все согласованные персонажи отображаются без ошибок.
- Любого персонажа можно пометить и вернуть одним нажатием.
- Анимация воспроизводится плавно и не сдвигает сетку.
- Состояние восстанавливается после обновления страницы.
- Общий сброс работает предсказуемо.
- Интерфейс помещается в согласованную область OBS.
- Управление через `Interact` не показывает служебный UI в эфире.
- Анимации не создают заметной нагрузки на GPU во время стрима.
- Проект проходит lint, проверку типов и production build.
- На опубликованной GitHub Pages нет битых путей к изображениям.
